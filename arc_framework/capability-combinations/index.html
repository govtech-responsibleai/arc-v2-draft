Capability combinations

Page Summary

Some risks belong to no single capability. They arise only when a system holds several capabilities at once. This page explains the four ways capabilities combine, and how ARC handles them: combination rules that bring a risk into scope whenever a system's capabilities can complete the combination, a list of the capabilities that give a system others, and a control for each rule. The lethal trifecta is the worked example.

Why combinations matter

Section titled “Why combinations matter”

ARC assesses a system one element at a time. Each capability brings its own risks, and each risk has its own controls. That works when the risks are independent of each other.

Some are not. Consider three agents:

  • An agent that only browses the web can be misled by what it reads, but it holds nothing worth stealing.
  • An agent that only reads internal files holds sensitive data, but no outsider can give it instructions.
  • An agent that does both can be told by a web page to open a file and send its contents to an address the attacker chose.

The third agent has a risk that neither of the first two has. Each of its capabilities can be well controlled on its own terms, so an assessment that looks at one capability at a time can pass a system that is exposed.

Other fields met this problem long before agents did. Auditors use segregation-of-duties matrices to find duties that no one person should hold together. Security researchers wrote rules for dangerous combinations of app permissions on mobile phones. Cloud security tools flag "toxic combinations" of findings that are minor alone. ARC applies the same idea to the capabilities of an agentic system.

Four ways capabilities combine

Section titled “Four ways capabilities combine”
Mechanism What combines Example with no attacker In register 2.0
Flow A capability that reads, and one that writes somewhere with a different level of trust Internal data pasted into a web search; web content saved into official records The lethal trifecta rule
Reach beyond the declared list Code Execution, Computer Use, System Management or Agent Delegation, with anything else An agent with code execution and network access can call any API, whether or not that capability was declared Capabilities that give a system others
Both sides of a check The capability to do something, and the capability to change what checks it An agent that writes code and also deploys it, or that acts and can also edit its own logs The oversight within reach rule, for an agent's own oversight
Loops A capability that writes where another reads Instructions planted in memory or in a file are read back in a later session Covered for persistent memory by the Memory component; not yet a rule

The first mechanism has been studied most. The lethal trifecta, Meta's Agents Rule of Two and information-flow defences such as CaMeL all address it. The second matters most to a framework like ARC, which assumes that the list of capabilities bounds what a system can do. Four capabilities break that assumption, because they produce or borrow other capabilities.

What ARC builds in

Section titled “What ARC builds in”

Roles. The register records what each capability can contribute to a combination, for example untrusted content or an outbound channel. A capability supplies a role wherever it is present (Yes), or only in some deployments (Maybe, with a note saying when). Some capabilities supply a role only from a certain authority upwards: Official Communication is an outbound channel when the agent sends messages itself, and not when a person sends what it drafts.

Rules. A rule names the roles that must all be supplied. Any capability that supplies a role will do, so a rule covers every pairing without listing them. A rule is:

  • present when every role is supplied by a capability marked Yes;
  • possible when every role is supplied, at least one only by capabilities marked Maybe;
  • not present when at least one role is supplied by none of the system's capabilities.

A rule that is present or possible brings its risks into scope, and its control must be implemented unless the assessor shows that a role is absent. The roles, rules and marks are in combinations.yaml, next to the risks and controls.

Composite risks. A risk can also list more than one element, and then applies only when the system has all of them. These risks arise from a rule or from several elements:

Risk Applies when
RISK-012 Cascading errors in multi-agent architectures The system has all of: Agentic Architecture (DSN-01) + Agent Delegation (CAP-02)
RISK-013 Man-in-the-middle attacks between agents The system has all of: Agentic Architecture (DSN-01) + Agent Delegation (CAP-02)
RISK-047 Data exfiltration through combined access to untrusted content, sensitive data, and an outbound channel The rule "Lethal trifecta" is present or possible: the system's capabilities can supply untrusted content, sensitive data, outbound channel
RISK-049 Escape from evaluation or sandbox containment onto live systems The system has all of: Roles and Access Controls (DSN-02) + Code Execution (CAP-10)
RISK-051 Unsanctioned coordination between agents The system has all of: Agentic Architecture (DSN-01) + Agent Delegation (CAP-02)
RISK-053 Dependence on third-party agents as counterparties or delegates The system has all of: Protocols (CMP-05) + Agent Delegation (CAP-02)
RISK-062 Agent alters or disables the oversight placed on it The rule "Oversight within reach" is present or possible: the system's capabilities can supply its own safeguards

Register 2.0 has two rules: the lethal trifecta, and oversight within reach.

The lethal trifecta

Section titled “The lethal trifecta”

An agent holds the lethal trifecta, a term coined by Simon Willison, when it has all three of the following:

  1. Untrusted content. Content that someone outside the organisation's control can write reaches the agent.
  2. Sensitive data. The agent can read data that would cause harm if it left the organisation.
  3. An outbound channel. The agent can cause data to reach a destination outside the organisation's control.

LLMs cannot reliably tell instructions from data, so text in a web page, an email, or a document can direct an agent that reads it. With all three legs in place, one injected instruction is enough. The agent reads the sensitive data and sends it out through a channel it is allowed to use. No control is bypassed, because every step is something the agent is permitted to do.

This has happened. In EchoLeak, a single crafted email led Microsoft 365 Copilot to send internal data to an attacker. In ForcedLeak, instructions in a web-form submission led Salesforce Agentforce to send out customer records. The Frontier Model Forum's brief on agent security recommends that, in higher-risk uses, no agent hold all three. Meta's Agents Rule of Two gives similar advice.

Which capabilities supply each leg

Section titled “Which capabilities supply each leg”

A capability can supply a leg wherever it is present, or only in some deployments.

Capability Untrusted content Sensitive data Outbound channel
Planning and Goal Management (CAP-01) – – –
Agent Delegation (CAP-02) Maybe – Maybe
Tool Use (CAP-03) – – –
Multimodal Understanding and Generation (CAP-04) Maybe – Maybe
Official Communication (CAP-05) Maybe – Yes
Business Transactions (CAP-06) – Maybe Yes
Internet and Search Access (CAP-07) Yes – Yes
Computer Use (CAP-08) Yes Yes Yes
Other Programmatic Interfaces (CAP-09) Maybe Maybe Maybe
Code Execution (CAP-10) Maybe – Maybe
File and Data Management (CAP-11) Maybe Yes –
System Management (CAP-12) – Yes Maybe

Yes means the capability supplies the leg wherever it is present. Maybe means it depends on the deployment, and the notes below say when. Planning and Goal Management and Tool Use supply no leg by themselves.

When each capability supplies a leg

Untrusted content. Content that someone outside the organisation's control can write reaches the agent.

  • Agent Delegation (CAP-02): maybe. Yes if it takes output from agents that other parties operate, or from agents that read untrusted content themselves.
  • Multimodal Understanding and Generation (CAP-04): maybe. Yes if its users are members of the public, or can upload or paste documents, images, or audio that someone else wrote.
  • Official Communication (CAP-05): maybe. Yes if it also reads replies or other inbound messages on the channels it sends through.
  • Internet and Search Access (CAP-07): yes. Web pages and search results can be written by anyone.
  • Computer Use (CAP-08): yes. Whatever appears on screen reaches the agent, including web pages, emails, and documents written by others.
  • Other Programmatic Interfaces (CAP-09): maybe. Yes if any API, queue, or mailbox it reads carries content from outside parties, such as inbound email, support tickets, form submissions, or webhooks.
  • Code Execution (CAP-10): maybe. Yes if it runs or reads code, packages, or repositories that outside parties can change.
  • File and Data Management (CAP-11): maybe. Yes if any file or data store it reads holds content from outside parties, such as uploads, shared drives, or records created from customer input.

Sensitive data. The agent can read data that would cause harm if it left the organisation, such as personal data, credentials, or confidential records.

  • Business Transactions (CAP-06): maybe. Yes if it holds payment credentials, or can read account, order, or customer records.
  • Computer Use (CAP-08): yes. It can see whatever the signed-in user can open on the machine.
  • Other Programmatic Interfaces (CAP-09): maybe. Yes if any API it can call returns personal, confidential, or credential data.
  • File and Data Management (CAP-11): yes. It reads the organisation's files, databases, or knowledge bases.
  • System Management (CAP-12): yes. System administration reaches configuration, credentials, and logs.

Outbound channel. The agent can cause data to reach a destination outside the organisation's control.

  • Agent Delegation (CAP-02): maybe. Yes if it can pass data to an agent that another party operates, or to an agent that has an outbound channel of its own.
  • Multimodal Understanding and Generation (CAP-04): maybe. Yes if its output is shown to people outside the organisation, or is rendered in a way that loads external images or links.
  • Official Communication (CAP-05): yes, from act with approval upwards. It sends messages to people outside the organisation.
  • Business Transactions (CAP-06): yes, from act with approval upwards. Transactions carry data to external parties in payment references, order details, and booking fields.
  • Internet and Search Access (CAP-07): yes. Any request to a web address can carry data in the URL or the query.
  • Computer Use (CAP-08): yes. It can use any application on the machine that sends data, including the browser and the mail client.
  • Other Programmatic Interfaces (CAP-09): maybe. Yes if any API it can call writes to a system outside the organisation, or accepts a destination that the agent chooses.
  • Code Execution (CAP-10): maybe, from act with approval upwards. Yes if the environment its code runs in can make network requests.
  • System Management (CAP-12): maybe, from act with approval upwards. Yes if it can change network, sharing, or access settings so that data becomes reachable from outside.

Components are not in the table. Persistent memory can carry untrusted content or sensitive data from one session into a later one, so count what memory holds when you answer for each leg.

The verdict

Section titled “The verdict”
Verdict When What to do
Present Every leg is supplied by a capability marked Yes Implement the control below
Possible Every leg is supplied, but at least one only by capabilities marked Maybe Answer the note for each of those capabilities from the system's code and configuration. If every leg is confirmed, implement the control. If a leg is absent, waive the control and record the evidence
Not present At least one leg is supplied by no capability Waive the control wherever it is listed, and record which leg is absent

The control is:

CTRL-0097 (Level 0 · Cardinal). Do not give one agent untrusted content, access to sensitive data, and an unrestricted outbound channel at once; remove one, or gate the outbound channel outside the agent.

It is a Level 0 control. Scoring does not waive it. It is waived only when a leg is absent, in the same way that any Level 0 control is waived when the capability or component it concerns is not present.

There are three ways to break the combination:

  • Split the agent. Give the untrusted content to a separate agent that has no access to sensitive data and returns only structured values.
  • Remove the data. Take away the sensitive data that the task does not need.
  • Gate the channel. Restrict the outbound channel outside the agent. Limit recipients and destinations to a fixed allowlist, and require human approval for any message or call that carries data to a new recipient.

The verdict describes the system as a whole. The control applies to each agent, so in a multi-agent system, record which agent holds each leg. Splitting the legs across agents satisfies the control only if the agent that reads untrusted content cannot pass free text to the agent that holds the data or the channel.

Oversight within reach

Section titled “Oversight within reach”

The second rule is the simplest case of holding both sides of a check: an agent that can change the logs, monitors, permissions, approval settings, or configuration that are meant to constrain it. Agents have done this in pursuit of a task, with no attacker involved, and have been made to do it by injected content. The rule has one role.

Capability Its own safeguards
Planning and Goal Management (CAP-01) –
Agent Delegation (CAP-02) –
Tool Use (CAP-03) –
Multimodal Understanding and Generation (CAP-04) –
Official Communication (CAP-05) –
Business Transactions (CAP-06) –
Internet and Search Access (CAP-07) –
Computer Use (CAP-08) Maybe
Other Programmatic Interfaces (CAP-09) –
Code Execution (CAP-10) Maybe
File and Data Management (CAP-11) Maybe
System Management (CAP-12) Yes
When each capability supplies the role

Its own safeguards. The agent can change the logs, monitors, permissions, approval settings, or configuration that are meant to constrain it.

  • Computer Use (CAP-08): maybe. Yes if it can open the settings of the application or platform that runs it.
  • Code Execution (CAP-10): maybe, from act with approval upwards. Yes if code it runs can reach the files, services, or settings that hold its permissions, approvals, logs, or monitors.
  • File and Data Management (CAP-11): maybe, from act with approval upwards. Yes if its write access covers its own instruction, configuration, or log files.
  • System Management (CAP-12): yes, from act with approval upwards. It manages access controls, monitoring, and configuration, which can include its own.

When the rule is present or possible, RISK-062 is in scope and this control applies:

CTRL-0101 (Level 0 · Cardinal). Give agents no write access to their own instructions, configuration, permissions, logs, or monitors.

A capability used only to read does not supply the role. The control is met when no identity, tool, or code path the agent has can write to what governs it, which is something to check for code execution and computer use as well as for the agent's named tools.

Capabilities that give a system others

Section titled “Capabilities that give a system others”

ARC assesses a system by the capabilities it declares. Four capabilities can give a system more than was declared: code can call anything its environment lets it reach, a computer-use agent can open any application, an administrator can grant itself access, and a delegating agent borrows what its delegates can do. Controls placed on the agent's named tools do not bind what it does by these routes.

Capability Also gives the system When
Agent Delegation (CAP-02) Any capability Maybe. The system has every capability held by an agent it can delegate to, including agents that another party operates. List those agents and their capabilities.
Computer Use (CAP-08) Internet and Search Access (CAP-07) Maybe. Yes if a browser is installed on the machine it operates.
Computer Use (CAP-08) Other Programmatic Interfaces (CAP-09) Maybe. Yes if the machine has applications or a terminal that call other systems.
Computer Use (CAP-08) Code Execution (CAP-10) Maybe. Yes if it can open a terminal, a code editor, or any application that runs scripts.
Computer Use (CAP-08) File and Data Management (CAP-11) Yes. It can open, change, and delete whatever files the signed-in user can.
Computer Use (CAP-08) System Management (CAP-12) Maybe. Yes if the signed-in user can change system settings or access controls.
Code Execution (CAP-10) Other Programmatic Interfaces (CAP-09) Maybe. Yes unless the environment its code runs in blocks network access.
Code Execution (CAP-10) File and Data Management (CAP-11) Yes. Code can read and write whatever files the account it runs under can.
Code Execution (CAP-10) System Management (CAP-12) Maybe. Yes if credentials for infrastructure, deployment, or administration are within reach of the code it runs.
System Management (CAP-12) File and Data Management (CAP-11) Maybe. Yes if it can grant itself access to data stores it was not given.

For each row that applies to a system, either add the implied capability to the assessment, or record the evidence that it does not apply, such as a sandbox with no network access and no credentials in reach.

Using the check in an assessment

Section titled “Using the check in an assessment”
  • In the developer guide: the check is part of Step 2, after the applicable risks are listed.
  • In the assessment template: Section 2a records the verdict, the answer for each leg, and how the combination is broken.
  • With a coding agent: the ARC assessment skill runs the check. arc.py assess prints the verdict and the notes to answer for the capabilities given.

Limits

Section titled “Limits”
  • Two rules so far. Register 2.0 has rules for the lethal trifecta and for an agent's reach over its own oversight. Other pairings of a capability with the check on it, such as writing code and deploying it, and loops other than persistent memory, are described above but have no rule yet.
  • Capabilities are coarse. Internet and Search Access covers reading pages and posting to them. Many systems will therefore get a verdict of Possible, and the notes turn that verdict into questions that evidence can answer.
  • Implied capabilities are reported, not added. The check lists the capabilities a system probably also has. It leaves the decision to the assessor, who adds them or records why they do not apply.
  • Design time only. The check reads what a system can do, not what it does in a given session. CTRL-0090 covers enforcement at run time.
